# 凭据保存前实时验证，恢复备份不覆盖凭据

**TL;DR**：写 token / 密码等凭据的配置接口，保存前用真实请求验证一次（401 直接拒绝保存），能终结"保存了坏 token → 周期性 bad_token → 重输又坏"的死循环；同时，从远端恢复备份时**凭据字段永远保留本地**，远端旧备份只覆盖业务数据。

## 问题
gh-release-center：GitHub Token 保存后能正常拉取，过一段时间提示 `bad_token`(401)，重新输入又能用、之后又坏，反复循环。

## 根因
存储链路本身正确，问题在两条**无效凭据被写入磁盘**的途径：
1. 前端允许保存任意字符串——手滑 / 失效旧 token 也落盘，之后每次请求都 401
2. WebDAV `pull`（恢复）整文件覆盖 data.json——远端旧备份（含失效/空白 token）把本地配置盖坏

## 解决
1. **保存前实时验证**：`PUT /api/settings` 写入新 token 前，先用它请求 `api.github.com/repos/octocat/Hello-World`——`401 bad_token` 直接拒绝保存并提示，杜绝无效 token 落盘；网络故障（proxy 不通等）不拦截，避免误伤
2. **恢复备份凭据保护**：WebDAV pull 时保留本地 `githubToken / proxy / webdavPass`，远端旧备份只覆盖业务数据（software 等），不再覆盖凭据

## 预防
1. 凡涉及"可粘贴的凭据"配置接口，一律**保存前验证**（用真实 API 的最小请求），验证失败就拒绝保存——校验成本远低于事后排障
2. "恢复 / 同步"类功能引入新数据源（文件、远端备份）时，问一句：**会不会把本地凭据盖掉？** 凭据字段必须从合并范围中排除
3. 网络故障时放行保存（不拦截），避免"断网状态下存不上配置"的体验问题；但要记录并提示
