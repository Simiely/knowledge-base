# 快照式同步的删除传播：墓碑机制三配套

**TL;DR**：快照式同步（整文件拉取合并）里"删除"无法天然传播——远端旧备份还有已删条目，下次同步又被拉回来。业界标准解法是**墓碑（tombstone）**，且必须三配套齐活：软删除 + 合并规则 + TTL 清理，任何一步缺失都会导致"已删数据复活"或"远端备份被覆盖"。

## 问题
本地删除账号后，远端旧备份仍有该账号，下次同步 smart 合并把它拉回来（"远端有、本地无"无法区分"你删了"与"从未存在"）。删除始终不跨设备传播。

## 根因
快照同步以"整份数据"为同步单元，只有存在性信息，没有"删除"这一可观察、可同步的变更。简单物理删除 = 信息丢失，合并时无从得知。

## 解决
墓碑机制三配套（edge-multi-account-cookie v2.10+ / workbuddy-credits-tool 均采用）：
1. **软删除**：删除时保留骨架 `{deleted:true, deletedAt}`，清空实际数据，使删除成为可同步的变更
2. **合并规则（复活判定）**：远端活跃 vs 本地墓碑 → 仅当 `inc.updatedAt > deletedAt` 才复活；远端墓碑 vs 本地活跃 → 本地 `updatedAt > 墓碑时间` 保留，否则删除传播
3. **TTL 物理清理（时机最关键）**：墓碑过期（约 30 天）后才物理删除，且**必须先传播到远端、再清理本地**——在合并/导入阶段提前 purge 会导致远端备份丢失删除标记 → 其他设备已删账号复活（P0 事故，见下方教训）

另两条关键语义：
- **清空本地 ≠ 删除**：`clearAll`（从网络端恢复的意图）仅本机物理清空、不生成墓碑；逐条删除才走墓碑传播。二者混用会让"清空"误删所有设备数据
- **上传前兜底**：合并后条目为 0 时跳过上传，杜绝"清空 + 远端无备份"把空数据覆盖远端备份

## 预防
1. 做同步功能先想"删除怎么传播"，再动手；墓碑是标准答案但不是银弹——**三配套缺一不可**
2. 墓碑清理时机必须是「先传播后清理」；改墓碑链路后跑回归：过期墓碑 + 再次同步 → 远端标记不丢 + 第三方设备不复活
3. 区分两类用户意图：清空（本地恢复）走物理删库、删除（全设备消失）走墓碑传播，UI 文案与实现都要区隔
4. 升级兼容：旧版本产生的墓碑残留可能导致"小墓碑覆盖远端完整备份"（实测 459KB 备份被同步成 5.6KB），升级路径要给出"先清空本地再同步"的迁移指引
