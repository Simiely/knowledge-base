# 历史快照数据建模：去重键 + 上限 + 时间升序

**TL;DR**：写"追加型"历史数据（快照/日志/趋势）时，必须提前定义三件事：去重键、条数上限、读取时的排序契约，否则数据爆炸、趋势失真。

## 问题
历史快照条数爆炸、折线图抖动、趋势方向颠倒——手动刷新与自动刷新重叠时一分钟产生多条快照，且快照数组顺序不保证时间升序。

## 根因
三个建模缺陷叠加：
1. 每次成功刷新都无条件 `appendSnapshot`，无去重（连点/并发时一分钟多条）
2. 无条数上限，历史无限膨胀
3. 读取处直接按数组顺序使用，未按时间排序（注入/写入顺序不可靠）

## 解决
- **去重键**：快照 `ts` 的 ISO 分钟前缀，该分钟内已有快照则跳过
- **上限**：总量上限 500 条，超出裁掉最旧
- **排序契约**：所有历史读取处按 `ts` 时间升序排序（`.sort((a,b) => a.ts < b.ts ? -1 : 1)`），约定"时间升序"为历史 API 的输出契约

## 预防
写任何"追加型"历史数据，先定义这三件事再谈功能：
1. 去重键是什么（粒度：分钟/小时/天）
2. 上限多少（超出怎么裁）
3. 读取时的排序规则（升序契约统一在服务端保证）
